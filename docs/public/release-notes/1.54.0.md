# Doc-Ray 1.54.0

Searching sentence text is much faster. Searches that took several seconds on a
large corpus now use the text index that was already there.

## Who is affected

- **Anyone who searches the corpus** — in the browser, through the API, or as an
  AI agent. Searches return the same results as before, sooner.
- **Administrators**, who need to apply one database migration.

Nothing about what a search *returns* changes: results, ordering, pagination,
citations and permissions are all as they were.

## What was wrong

Sentence text has always had an index built for substring search. A permission
rule added early in the project's life made that index unusable, and nothing
reported it. PostgreSQL will not test whether a sentence matches your search
before checking whether you are allowed to see that sentence, because doing so
could reveal that a document you cannot read contains your search term.

So every search read every sentence in the corpus. On a corpus of roughly two
million sentences a single-word search took about 3.8 seconds to return one page
of results, and the cost grew with the size of the corpus rather than with the
number of matches.

## What changed

Finding candidate sentences now happens inside a dedicated database routine that
applies your document permissions itself, explicitly, before returning anything.
That lets the database use the text index again.

Permissions are unchanged. The routine resolves *your* identity rather than its
own and returns only sentences from documents you may read; administrators
continue to see everything in their tenant. Tests cover this directly, including
that one user cannot reach another user's documents through the new path.

One case is unchanged: searching for a word of one or two letters, such as `of`
or `it`, still cannot use the index, because an index of this kind needs at
least three characters to work with. Those searches were already fast, because
they reach the result limit almost immediately.

## Action required

**Administrators:** apply the database migration as usual.

```bash
make prod-migrate
```

It adds one routine. No table, column or permission policy changes, and no data
is rewritten, so it applies quickly on a corpus of any size. No configuration
changes.

**Everyone else:** nothing. No query, integration or saved search needs to
change.
