# 1.53.1 — Honest sentence retrieval

## Whole-word phrase search

Sentence search now offers an explicit phrase mode without redefining existing
queries. Omitting `match` remains case-insensitive literal substring matching.
Opting into `PHRASE`/`phrase` verifies whole words and adjacency under
`surface_word_v1`; it does not stem, so `algorithm design` rejects `algorithm
designed`, and `ngram` rejects `Tangram`.

GraphQL example:

```graphql
query ExactSentencePhrase($document: ID!) {
  searchSentencePage(
    term: "Algorithm Design"
    documentId: $document
    match: PHRASE
    limit: 20
  ) {
    matchProfile
    candidateScanned
    candidateLimit
    candidateLimitReached
    hits {
      id
      ordinal
      pre
      hit
      post
      occurrenceCount
      occurrences { charStart charEnd }
      cursor
    }
  }
}
```

MCP example:

```json
{"name":"search_sentences","arguments":{"term":"Algorithm Design","document_id":"…","match":"phrase","limit":20}}
```

The MCP result adds `matchProfile: "surface_word_v1"`; each hit lists all
absolute half-open Document offsets and KWIC quotes the first one. Coverage adds
`candidate_scanned`, `candidate_limit`, and `candidate_limit_reached`. A cap hit
is non-exhaustive even if verification emitted zero rows. The webapp exposes the
same mode through the off-by-default **Whole phrase** checkbox.

This is an additive application feature: no schema migration, reindex, token
backfill, environment/configuration change, or client SDK update is required.
Existing GraphQL and MCP calls retain substring behavior.

## Verified phrase-frequency counts

`termFrequency` and MCP `term_frequency` now use the same versioned
`surface_word_v1` occurrence definition as phrase search. The bounded SQL stage
fetches a permissive, index-backed candidate superset; a pure verifier removes
word-internal, reordered, inflected, or punctuation-separated false positives
and counts every overlapping occurrence.

The additive flat fields make each quantity unambiguous:

- `sentenceHits` — candidate sentences fetched before the cap;
- `occurrenceSentences` — candidates with at least one verified occurrence;
- `occurrences` — all verified overlapping starts;
- `profile` — `surface_word_v1`.

`attested` and `floodRisk` use `occurrenceSentences`. The invariant is
`occurrences >= occurrenceSentences <= sentenceHits`. If `capped` is true, all
three counts are floors because unseen candidates may add verified matches; the
verdict is therefore high/incomplete. A capped verified zero leaves `attested`
null; only an uncapped verified zero supports an absence claim.

```graphql
query VerifiedPhraseFrequency {
  termFrequency(terms: ["Algorithm Design", "shared_buffers"]) {
    term method profile
    sentenceHits occurrenceSentences occurrences
    totalSentences capped floodRisk attested note
  }
}
```

MCP exposes the identical fields:

```json
{"name":"term_frequency","arguments":{"terms":["Algorithm Design","shared_buffers"]}}
```

Exact single-lexeme rows remain unchanged with `method: "lexeme_lemma"` and null
scan fields. This is an additive application contract: there is no database
migration, reindex, token backfill, environment/configuration change, or SDK
release for #46.

## Honest sentence denominators

Issue #42 exposed an impossible result from the phrase-frequency pre-flight:
positive `sentenceHits` paired with `totalSentences: 0`. The scan was real; the
maintained tenant denominator was stale because the deploy-time full-refresh path
did not write the column introduced in 1.52.0.

Version 1.53.1 repairs and backfills that rollup. If a future integrity fault makes
the denominator unavailable, both supported client contracts now return
`totalSentences: null` and an explanatory `note`. They retain the measured hit count
and absolute hit-band `floodRisk`; they never turn the contradiction into “N of 0.”
A genuinely empty visible corpus still reports zero hits out of zero sentences.

## GraphQL API

```graphql
query PhraseFloodRisk {
  termFrequency(terms: ["Model Context Protocol", "shared_buffers"]) {
    term
    method
    profile
    sentenceHits
    occurrenceSentences
    occurrences
    totalSentences
    capped
    floodRisk
    attested
    note
  }
}
```

Normal result:

```json
{"data":{"termFrequency":[{"term":"Model Context Protocol","method":"sentence_scan","profile":"surface_word_v1","sentenceHits":48,"occurrenceSentences":43,"occurrences":47,"totalSentences":1954674,"capped":false,"floodRisk":"low","attested":true,"note":null}]}}
```

Integrity-degraded result:

```json
{"data":{"termFrequency":[{"term":"Model Context Protocol","method":"sentence_scan","profile":"surface_word_v1","sentenceHits":48,"occurrenceSentences":43,"occurrences":47,"totalSentences":null,"capped":false,"floodRisk":"low","attested":true,"note":"The total-sentence denominator is unavailable because corpus_stats rollup is empty; occurrenceSentences remains measured, floodRisk uses absolute bounded verified-sentence bands."}]}}
```

`totalSentences` was already nullable in the GraphQL schema, so the wire schema is
backward compatible. Clients that assumed it was always numeric must handle `null`
and show the accompanying note.

## MCP

Call the existing read tool; its response uses the same fields and semantics:

```json
{"name":"term_frequency","arguments":{"terms":["Model Context Protocol","shared_buffers"]}}
```

`capped: true` means `sentenceHits`, `occurrenceSentences`, and `occurrences` are
all floors. A null `totalSentences` means the denominator is unavailable, not
zero; `floodRisk` remains usable because sentence-scan bands use the bounded
verified sentence count.

Doc-Ray publishes no client SDK, so there is no separately versioned SDK to update.
GraphQL and MCP are the supported integration contracts and are aligned above.
